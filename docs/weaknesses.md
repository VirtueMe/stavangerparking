# Known weaknesses

A running log of trade-offs and known limitations, recorded when they appear rather than reconstructed at the end. Every issue that makes a trade-off adds an entry here before it is closed.

| Weakness | Consequence | Mitigation | Related |
|---|---|---|---|
| The source feed has not updated since 23.09.2026 19:16 (checked on 28.09.2026), although the file is re-published every 2 minutes (CKAN `last_modified`, HTTP `Last-Modified` and ETag all move). Historically the data was 2–4 minutes old | A fresh file does not mean fresh data: collected snapshots repeat the same values, and gaps in history cannot be recovered afterwards | Staleness detection in silver compares the source timestamp in the data, not file or metadata dates; raise it with the data owner | #10, [ADR 003](adr/003-polling-interval.md) |
| The source only exposes the current state, not history | Any period without collection is lost for good | Start collecting early, outside the data platform | #6, [ADR 007](adr/007-collect-outside-the-platform.md) |
| Resolving the download URL through the CKAN API makes it a second dependency, called without retries (10 s timeout) | An API hiccup costs one snapshot, even if the file itself is reachable | The next scheduled run tries again, and a failed run is visible; add retries if failures turn out to be frequent | #4 |
| More than one JSON resource in the package stops ingestion instead of picking one | Ingestion halts until someone decides which resource is right | Deliberate: a wrong guess would silently land the wrong data. The config can name the resource if this happens | #4, #3 |
| Collection runs on GitHub Actions while platform access is pending, started by an external scheduler, cron-job.org, because GitHub's own schedule started only 2 of about 145 expected runs in the first 12 hours after #6 was merged (2026-09-28 16:32 → 2026-09-29 04:48 UTC). GitHub describes scheduled runs as best effort: they *"may be delayed or potentially dropped"* | cron-job.org is a dependency with no fallback: if it stops, or its token expires or is revoked, no runs start; the minimum interval is still 5 minutes | cron-job.org e-mails when a call fails, but nothing alerts when calls stop altogether; until staleness detection (#10) and failure alerts (#19) exist, check for gaps from the sidecars (`collect gaps`); runs can be started by hand; raw files are the source of truth, so bronze can be rebuilt from them. Move ingestion into the platform when access is available | #6, #49, #10, #19, #18, [ADR 007](adr/007-collect-outside-the-platform.md), [ADR 008](adr/008-trigger-collection-externally.md), [community discussion #185355](https://github.com/orgs/community/discussions/185355) |
| The token that starts the collector is stored at a third party (cron-job.org), and it expires | A leaked token can start, cancel and delete workflow runs and disable the workflow in this repository, so it could stop collection, but it cannot change code, push data or read secrets. An expired token stops collection | Fine-grained token limited to this repository and *Actions: read and write*; revoke it on GitHub if leaked; rotate before expiry ([rotating the token](collector.md#rotating-the-token)) | #49, [ADR 008](adr/008-trigger-collection-externally.md) |
| Polling every 5 minutes while values change and keeping every fetched snapshot creates up to 288 small files and bronze commits per day, up to about 105,000 raw files per year | Storage and table metadata grow with many tiny files; the `data` branch becomes slow to clone | Table maintenance (#20); raw files can be compacted or archived by month once bronze holds them | #20, [ADR 003](adr/003-polling-interval.md) |
| Polars on a single node is chosen for today's volume (about 1 million rows per year) | A large increase in sources, frequency or history would outgrow one machine | The Delta tables are engine-neutral; ADR 001 lists when to switch to Spark | #22, [ADR 001](adr/001-polars-over-pyspark.md) |
| Adaptive polling (every 20 minutes after 5 unchanged snapshots) makes observations irregular | Plain averages over observations would over-weight busy periods; a change after a quiet period is seen up to 20 minutes late, and changes within one 20-minute gap are missed | Facts treat each observation as valid until the next and use time-weighted averages; slow mode is only entered after 5 identical snapshots | #6, #13, #14, [ADR 003](adr/003-polling-interval.md) |
| Every collector run checks out the latest `data` branch tree and scans all sidecars to find the latest ones | Run time grows with the number of stored files (about 105,000 per year at most) | Fine for the case period; limit the checkout and scan to the most recent days if runs slow down | #6 |
| A run that fails between writing the raw file and its sidecar leaves a raw file without sidecar | The file is ignored by the polling decision and the gap listing | The files are written back to back and pushed together; bronze loading records raw files without a sidecar in `bronze_parking_load_issues` and reports them | #6, #7 |
| The source has no visible support channel. The dataset page on opencom.no has no support, feedback or "report a problem" link; the only contact is the maintainer's address `opendata@stavanger.kommune.no`, in the "Tilleggsinformasjon" table near the bottom. Stavanger Parkering, which owns the data, is not named as a contact | A feed that stops updating can go unnoticed and unreported; consumers have no clear route to the people who can fix it | Report through `opendata@stavanger.kommune.no` and ask them to forward to Stavanger Parkering; for production use, agree on a support channel and a service level with the data owner | #45 |
| Every "updated" signal of the source reflects the re-upload of the file, not new data: "Sist oppdatert" on the dataset page, CKAN `last_modified` and `metadata_modified`, HTTP `Last-Modified`, and the ETag (Werkzeug's `"{mtime}-{size}-{adler32(filename)}"`, which changes with the file's modification time, not its content). Caching was ruled out: the server sends `Cache-Control: no-cache`, and cache-busted requests return the same bytes | The frozen feed looks fresh on the website and in the API; only comparing content reveals it | Never use metadata dates or ETags as freshness signals: the collector compares `content_hash` and `values_fingerprint`, and staleness detection uses the data's own timestamp | #6, #10, #45, [ADR 003](adr/003-polling-interval.md) |
| Bronze loading decides what is new by reading the whole `raw_file` column of bronze (and the load issues) on every run | The cost of each load grows with the full history, not with the number of new files | Negligible at about 1 million rows per year; if it matters, scan only recent partitions or keep a small manifest of loaded files | #7 |
| The source gives Oslo local time without a UTC offset. At the autumn DST change, 02:00–02:59 happens twice, and silver picks the later candidate unless it lies after the fetch time (`ingested_at`) | If the source is stale across the change, a reading from the first pass that is fetched during the second pass is placed one hour late | `dst_resolved` marks every reading resolved this way; staleness detection (#10) can flag the ones fetched long after their source time. At most one hour per year is affected | #8, #10, [docs/silver.md](silver.md#oslo-time) |
| Silver parses only new bronze rows, but finds them by reading the row keys of the fetch table and quarantine, and derives readings and conflicts from all fetches on every run | Build time grows with the full history, not with the new rows | Deliberate: deriving from all fetches is what makes incremental runs equal a rebuild. Negligible at about 1 million fetches per year; if it matters, limit the derivation to the dates the new fetches touch | #8, #9 |
| Staleness is judged per snapshot, from its newest source timestamp | A single facility whose value stops updating while the others advance is not detected; neither is a source that keeps advancing its timestamp without new values | All facilities have always shared one timestamp; per-facility checks, such as unchanged values over a long busy period, belong to the quality checks (#21) | #10, #21 |
| A stale period ends at the last fetch that saw it stale | Stale time between that fetch and the source's recovery is not counted: up to one fetch interval (5 or 20 minutes) per period, or longer across a gap in collection | Deliberate: counting it would claim staleness without evidence. Gaps in collection are listed separately (`collect gaps`) | #10, #14 |
| The facility name in the feed is the natural key; the feed has no id | A renamed facility appears as a new facility, and its history is split between two rows | The old name is marked inactive, not deleted; a rename is detectable (one facility stops and another starts at nearly the same place) and can be mapped in the mapping file if it happens | #12, #21, [ADR 004](adr/004-facility-name-as-natural-key.md) |
| Capacity comes from Parkeringsregisteret through a hand-maintained name mapping. On 2026-09-29 the register and the operator's website disagreed for Jernbanen (390 vs 500) and Forum (289 vs 325) | Occupancy is only as right as the register; a facility missing from the mapping has no capacity | Register snapshots are collected hourly (ADR 010), so changes arrive within the hour without manual edits; discrepancies are noted in the mapping; `free spaces > capacity` and unmapped facilities are checked (#21) | #12, #21, #54, #60, [ADR 005](adr/005-capacity-as-reference-data.md) |
| `dim_date` marks only the 13 official public holidays | Days that change parking behaviour without being holidays are not marked: Christmas Eve and New Year's Eve (half days), school holidays, and events such as Gladmat or concerts | Enough to separate holidays from ordinary days; school holidays (Rogaland county) and an events calendar could be added as reference data if the analyses need them | #11 |
| `dim_date` covers a fixed range, 2020–2035 | Readings after 2035 would have no date key | Extend `LAST_DATE`; the facts check that every reading has its date key (#13) | #11, #13 |
| Facility keys are kept by MERGE rather than recomputed | A dimension built from scratch can number facilities differently from one built up run by run, so keys are not comparable across separate builds | Facts are always built from the same dimension, so the model is consistent; nothing outside the model should store facility keys | #12 |
| Occupancy uses each facility's current capacity for all of history, and the register can be wrong: Forum reported 292 free spaces on 23 September 2026 against the register's 289 | Occupancy is off by the capacity error, and can be negative | Negative occupancy is shown, not hidden, and flagged by the quality checks (#21); the discrepancy is noted in the facility mapping. Historical capacities (from the register's versions) could replace the current one if they matter | #13, #21, [ADR 005](adr/005-capacity-as-reference-data.md) |
| The hourly fact assumes a reading holds until the next one, for up to one slow polling interval (20 minutes) after the last fetch that saw it | Within that window, changes the collector did not see are missed: the source publishes every 2 minutes, the collector fetches every 5 or 20 | `covered_minutes` shows where there is no evidence at all; the window is the collector's own worst-case interval, so normal operation is fully covered and gaps are not | #14, [ADR 003](adr/003-polling-interval.md) |
| Only the register's mapped areas are stored: the raw file is a filtered copy of the response, an exception to storing responses unchanged | A new facility's register history before it is mapped cannot be recovered; the raw file alone does not show the other areas | The sidecar records the full response's hash and record count; each kept record is unchanged; a facility has no capacity until it is mapped anyway | #60, #62, [ADR 007](adr/007-collect-outside-the-platform.md#addendum-2026-09-29-filtered-raw-files-for-reference-data), [ADR 010](adr/010-collect-the-register-hourly.md) |
